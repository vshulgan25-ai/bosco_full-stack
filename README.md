## 1. Огляд проєкту та архітектура монорепозиторію

**«Система управління стипендіальними програмами учнів Центру професійної освіти Боско»** — це сучасний Fullstack-проєкт, розроблений для автоматизації процесів призначення, публікації та подання заявок на стипендії для учнів 2025–2026 навчального року у Центрі професійної освіти св. Івана Боско (м. Львів).

### Головні переваги обраної архітектури:
1. **Монорепозиторій:** Бекенд (`/cms`) і фронтенд (`/frontend`) об'єднані у спільний кореневий маніфест `package.json`, що спрощує версіонування, спільну розробку та синхронізацію типів.
2. **Headless CMS на базі коду:** Використання **Payload CMS 3.x** дозволяє описувати всі таблиці бази даних, зв'язки, права доступу та поля безпосередньо у коді TypeScript. Адміністративна панель генерується повністю автоматично, без потреби ручної верстки адмінки.
3. **Хмарна реляційна СУБД:** База даних розгорнута на серверлес-платформі **Neon PostgreSQL**. Це вирішує проблему ефемерного файлового сховища (ephemeral storage) платформи Vercel, забезпечуючи високу надійність та персистентність даних.
4. **Легковагий та швидкий клієнт:** Фронтенд побудований на сучасному бандлері **Vite**, чистому **TypeScript** та нативному модульному **Vanilla JS** (без надлишкових важких фреймворків). Це гарантує миттєве завантаження сторінки, високий бал Google PageSpeed та відмінну адаптивність.

```
       [ Клієнтський браузер ]
                  │
        (1) GET /api/common
        (2) GET /api/page?path=/
        (3) POST /api/apply
                  ▼
       [ Фронтенд: Vite + TypeScript ]
                  │  (CORS / Proxy)
                  ▼
       [ Бекенд: Payload CMS 3.x ]
       ├── /api/common  ──► Globals (Header, Footer)
       ├── /api/page    ──► Pages + ScholarshipPrograms
       └── /api/apply   ──► Applications
                  │
                  ▼  (DATABASE_URI, sslmode=require)
       [ Хмарна БД: Neon PostgreSQL ]
```

## 3. Розділ 3.1. Архітектура та Payload CMS (Бекенд)

### 3.1.1. Конфігурація Payload CMS та хмарна БД Neon PostgreSQL
Конфігурація бекенду зосереджена у файлі [`cms/src/payload.config.ts`](cms/src/payload.config.ts). Замість локальної файлової бази даних SQLite для забезпечення надійності у хмарному середовищі використано адаптер `@payloadcms/db-postgres`:

```typescript
import { postgresAdapter } from '@payloadcms/db-postgres'

export default buildConfig({
  // Підключення до хмарної бази даних PostgreSQL на платформі Neon
  db: postgresAdapter({
    pool: {
      connectionString: process.env.DATABASE_URI || '',
    },
  }),
  // ...
})
```
Рядок підключення `DATABASE_URI` отримується з налаштувань Neon із прапорцем `sslmode=require`, що гарантує захищене TLS-з'єднання між сервером додатків та базою даних.

### 3.1.2. Політика безпеки та CORS
Оскільки клієнтський застосунок на Vite працює за адресою `http://localhost:5173`, а сервер Payload CMS — на `http://localhost:3000` (а в продакшені на окремих доменах Vercel), налаштовано список дозволених джерел (CORS Origins):
```typescript
const allowedOrigins = process.env.CORS_ORIGINS
  ? process.env.CORS_ORIGINS.split(',').map((url) => url.trim())
  : ['http://localhost:5173', 'http://localhost:3000', 'http://127.0.0.1:5173']

export default buildConfig({
  serverURL: process.env.NEXT_PUBLIC_SERVER_URL || 'http://localhost:3000',
  cors: allowedOrigins,
  csrf: allowedOrigins,
  // ...
})
```
Це усуває помилки крос-доменної безпеки у браузері під час виконання HTTP-запитів `fetch()`.

### 3.1.3. Колекції системи
Всі структури даних описані як типізовані колекції Payload CMS:

1. **`Users`** ([`Users.ts`](cms/src/collections/Users.ts)):
   - Авторизація, паролі, права доступу.
   - Ролі: `admin` (головний адміністратор), `editor` (модератор/редактор), `student` (учень).
   - Суворі поля вибору (Select) для академічних груп: `IT-21`, `IT-22`, `AV-21`, `PO-22`, `KP-21`, `REM-21`, `EL-22`.
   - Номер курсу: 1, 2, 3.

2. **`ScholarshipPrograms`** ([`ScholarshipPrograms.ts`](cms/src/collections/ScholarshipPrograms.ts)):
   - `name`: назва стипендіальної програми.
   - `kind`: випадаючий список типів (`tuition` — навчання, `collegium` — колегіум, `cafe` — харчування у кафе «Мама Маргарита», `social` — соціальна, `merit` — досягнення).
   - `amount`: грошовий еквівалент у гривнях (10 000, 4 000, 200 тощо).
   - `amountNote`: примітка (щомісяця, за модуль, щодня).
   - `category`: цільова група учнів (ВПО, діти військових, мешканці колегіуму тощо).
   - `badge`: бейдж картки («Пріоритетна», «Гарячий обід»).
   - `isActive`: прапорець активності набору на 2025–2026 н.р.

3. **`Applications`** ([`Applications.ts`](cms/src/collections/Applications.ts)):
   - Збереження поданих учнями заяв.
   - `fullName`: ПІБ учня.
   - `group`: строгий селект групи учня.
   - `program`: зв'язок (relationship) з колекцією `scholarship-programs`.
   - `motivation`: мотиваційний лист.
   - `status`: поточний стан заявки (`pending` — на розгляді, `approved` — схвалено, `rejected` — відхилено).
   - `academicYear`: навчальний рік (2025/2026).
   - `reviewNote` та `reviewedAt`: висновок стипендіальної комісії.

4. **`Pages`** ([`Pages.ts`](cms/src/collections/Pages.ts)):
   - Сторінки сайту та їхні URL-шляхи (`path`).
   - Поле типу `blocks` (Page Builder), що включає: `HeroBlock`, `ProgramsBlock`, `AboutBlock`, `BenefitsBlock`, `ApplyFormBlock`.

5. **`Media`** ([`Media.ts`](cms/src/collections/Media.ts)):
   - Збереження графічних файлів, логотипів та документів.

### 3.1.4. Глобальні налаштування Globals
Елементи інтерфейсу, наскрізні для всього сайту, винесені в категорію `Globals`:
- **`Header`** ([`Header.ts`](cms/src/globals/Header.ts)): назва Центру, слоган, URL логотипу, перелік пунктів меню та кнопка заклику до дії (CTA).
- **`Footer`** ([`Footer.ts`](cms/src/globals/Footer.ts)): контактна адреса (вул. Дорога Кривчицька, 19д), телефон приймальної, розклад роботи, офіційні соцмережі та копірайт.

### 3.1.5. Кастомні API-ендпоінти
Стандартний REST API Payload CMS повертає глибоко вкладені метадані, які незручно обробляти на клієнті без зайвих перетворень. Для оптимізації створено три кастомні ендпоінти:
- **`GET /api/common`** ([`common.ts`](cms/src/endpoints/common.ts)): повертає плоский об'єкт із даними шапки, підвалу та загальної статистики.
- **`GET /api/page?path=/`** ([`page.ts`](cms/src/endpoints/page.ts)): знаходить сторінку за заданим шляхом, автоматично підтягує активні стипендіальні програми в блок `programs` та віддає чистий JSON-масив `blocks`.
- **`POST /api/apply`** ([`apply.ts`](cms/src/endpoints/apply.ts)): приймає дані заявки, валідує ПІБ, групу, коректність email, телефон та довжину мотиваційного листа (мін. 20 символів), після чого реєструє нову заявку зі статусом `pending`.

## 4. Розділ 3.2. Клієнтська частина та стани UI (Фронтенд)

### 3.2.1. Технологічний стек та модульний Vanilla JS на Vite
Клієнтська частина реалізована за концепцією Modular Vanilla TypeScript:
- **Vite:** швидкий сервер розробки з Hot Module Replacement (HMR) та оптимізований збірник у продакшен-бандл.
- **ES Modules (ESM):** розділення коду на ізольовані модулі за допомогою `import` та `export`.
- Відсутність важких UI-бібліотек забезпечує миттєвий TTI (Time to Interactive) та мінімальний розмір підсумкового JS-бандла (~40 KB проти кількох мегабайтів у стандартних SPA-фреймворках).

### 3.2.2. Життєвий цикл запиту та механізм динамічного рендерингу
Повний життєвий цикл запиту в системі відбувається за такими кроками:
1. Користувач переходить за посиланням або оновлює сторінку в браузері.
2. Скрипт [`main.ts`](frontend/src/main.ts) зчитує `window.location.pathname` та одночасно запускає два асинхронні `fetch`-запити:
   - `fetchCommonData()` ──► `GET /api/common`
   - `fetchPageData(path)` ──► `GET /api/page?path=...`
3. Отриманий масив блоків передається у диспетчер [`renderBlocks.ts`](frontend/src/renderBlocks.ts).
4. Диспетчер перебирає масив, за полем `block.type` знаходить відповідний модуль (`Hero.ts`, `Programs.ts`, `About.ts`, `Benefits.ts`, `ApplyForm.ts`), динамічно генерує DOM-елементи та монтує їх у контейнер `<main id="app-content">`.

### 3.2.3. Керування станами інтерфейсу (Loading / Error / Success)
Фронтенд надійно керує трьома станами UI за допомогою блоку `try...catch`:
- **Стан завантаження (Loading):** До моменту отримання даних від сервера користувач бачить скелетон із градієнтною анімацією мерехтіння (Shimmer effect) та спіннер, що усуває неприємні стрибки макета (Cumulative Layout Shift).
- **Стан готовності (Success):** Плавний монтаж згенерованих компонентів Header, Page Blocks та Footer, а також оновлення заголовка сторінки (`document.title`).
- **Стан помилки (Error):** Якщо бекенд тимчасово недоступний або в мережі виник збій, застосунок не ламається, а відображає картку помилки з кнопкою **«Спробувати знову» (Retry)**, яка перезапускає життєвий цикл, а також спливаючий Toast з інформацією про стан з'єднання. Модуль [`mockData.ts`](frontend/src/services/mockData.ts) з демонстраційними даними вмикається **лише явно** (`VITE_USE_MOCK=true`) і не маскує реальні помилки — завдяки цьому екран помилки гарантовано показується, коли бекенд недоступний.

## 5. Розділ 3.3. Сувора типізація на TypeScript

У клієнтській частині та на бекенді впроваджено строгий режим типізації (`strict: true`).

### 3.3.1. Використання Type Aliases та лінійних типів
У файлі [`common.ts`](frontend/src/types/common.ts) оголошено базові аліаси типів:
```typescript
export type ID = string | number
export type AcademicYear = '2025/2026' | '2026/2027'
export type UiStateStatus = 'idle' | 'loading' | 'success' | 'error'
```

### 3.3.2. Дискриміновані об'єднання (Union Types)
Для виключення людських помилок при виборі груп або статусів застосовано літеральні об'єднання типів:
```typescript
// Суворий список груп учнів Центру Боско
export type AcademicGroup =
  | 'IT-11' 
  | 'IT-12' 
  | 'A-11'
  | 'А-12' 
  | 'К-11'
  | 'М-11' 
  | 'Д-11' 

// Типи програм
export type ProgramKind = 'tuition' | 'collegium' | 'cafe' | 'social' | 'merit'

// Статуси розгляду заяви
export type ApplicationStatus = 'pending' | 'approved' | 'rejected'
```

Для блоків контенту сторінки використано патерн **Discriminated Union** у файлі [`blocks.ts`](frontend/src/types/blocks.ts):
```typescript
export type PageBlock =
  | HeroBlockData
  | ProgramsBlockData
  | AboutBlockData
  | BenefitsBlockData
  | ApplyFormBlockData

export type BlockType = PageBlock['type']
```

### 3.3.3. Типи перетину (Intersection Types)
Для розширення базових моделей додатковими властивостями без дублювання коду застосовано типи перетину:
```typescript
export type Identifiable<T> = T & {
  readonly id: ID
}

export type WithTimestamps<T> = T & {
  readonly createdAt: string
  readonly updatedAt?: string
}

// Приклад створення повної моделі стипендії з метаданими
export type CompleteProgramDetails = ScholarshipProgramItem &
  WithTimestamps<{
    readonly eligibilityRules?: readonly string[]
    readonly sponsorName?: string
  }>
```

### 3.3.4. Повна типізація функцій, API-контрактів та звуження типів (Type Guards)
У файлі [`blocks.ts`](frontend/src/types/blocks.ts) реалізовано спеціальні предикати типів (User-Defined Type Guards):
```typescript
export function isHeroBlock(block: PageBlock): block is HeroBlockData {
  return block.type === 'hero'
}

export function isProgramsBlock(block: PageBlock): block is ProgramsBlockData {
  return block.type === 'programs'
}
```
Це дає змогу компілятору TypeScript у коді безпечно визначати специфічні поля кожного блоку (наприклад, доступ до `block.stats` дозволено тільки після перевірки типу `hero`).

### 3.4.2. Розгортання на хмарному хостингу Vercel та інтеграція з Neon

Хостинг Vercel базується на безсерверній архітектурі (Serverless Architecture). У такій системі контейнери серверних функцій піднімаються на вимогу і завершують свою роботу після відповіді клієнту, а їхня файлова система є ефемерною (Ephemeral Storage), тобто будь-які локально створені файли (наприклад, SQLite-файл бази даних) безповоротно стираються при наступному холодному старті.

Саме тому для надійного збереження даних проєкту обрано зовнішню хмарну реляційну базу даних **Neon PostgreSQL**, яка підтримує постійне зберігання, автоматичне масштабування та пулінг з'єднань.

#### Порядок деплою монорепозиторію на Vercel:

1. **Деплой Бекенду (`/cms`):**
   - У панелі Vercel натисніть **Add New Project** та оберіть репозиторій з GitHub.
   - У полі **Root Directory** вкажіть папку `cms`.
   - Vercel автоматично визначить фреймворк **Next.js**.
   - У розділі **Environment Variables** додайте змінні:
     - `DATABASE_URI`: повний рядок підключення до Neon з `?sslmode=require`.
     - `PAYLOAD_SECRET`: секретний ключ шифрування.
     - `NEXT_PUBLIC_SERVER_URL`: URL вашого створеного Vercel-домену (наприклад, `https://bosco-cms.vercel.app`).
     - `CORS_ORIGINS`: URL майбутнього фронтенду (наприклад, `https://bosco-scholarships.vercel.app`).
   - Натисніть **Deploy**.

2. **Деплой Фронтенду (`/frontend`):**
   - Створіть другий проєкт у Vercel із того ж самого репозиторію.
   - У полі **Root Directory** вкажіть папку `frontend`.
   - Оберіть фреймворк **Vite**.
   - Додайте змінну оточення:
     - `VITE_API_BASE_URL`: URL задеплоєного раніше бекенду (наприклад, `https://bosco-cms.vercel.app`).
   - Натисніть **Deploy**.

#### Сценарій 3: Обробка мережевих збоїв та валідаційних помилок

1. **Клієнтська валідація:** Якщо учень пропускає обов'язкове поле (наприклад, не обрав групу або ввів менше 20 символів у полі мотиваційного листа), відправка блокується:
   - Некоректні поля підсвічуються червоною рамкою (`is-invalid`).
   - Під кожним полем виводиться текст підказки: *«Оберіть вашу академічну групу»*, *«Мотиваційний лист повинен містити щонайменше 20 символів»*.
   - З'являється жовте спливаюче Toast-сповіщення: *«Будь ласка, виправте виділені поля форми»*.

```text
┌────────────────────────────────────────────────────────────────────────┐
│  ПІБ учня:        [ Іван                                             ] │
│                   * Вкажіть повне Прізвище, Ім'я та По батькові        │
│                                                                        │
│  Академічна група:[ Оберіть вашу навчальну групу...                ▼ ] │
│                   * Оберіть вашу академічну групу                      │
│                                                                        │
│  [!] Toast: Будь ласка, виправте виділені поля форми                   │
└────────────────────────────────────────────────────────────────────────┘
```

2. **Серверна відмова / Збій мережі:** Якщо сервер Payload CMS тимчасово вимкнено або зникло інтернет-з'єднання:
   - Конструкція `try...catch` у файлі [`main.ts`](frontend/src/main.ts) перехоплює виняток без критичного падіння програми.
   - Замість порожнього білого екрана користувач бачить інформативну картку стану помилки:
     > ⚠️ **Не вдалося завантажити дані**  
     > Виникла мережева помилка під час зв’язку з сервером Payload CMS. Перевірте підключення до Інтернету.  
     > `[ Спробувати знову ]`
   - Клік на кнопку перезапускає функцію ініціалізації додатку. Для відтворення сценарію достатньо зупинити CMS (або вказати хибний `VITE_API_BASE_URL`) і оновити сторінку.

## 7. Висновок

Розроблений Fullstack-додаток **«Система управління стипендіальними програмами учнів Центру професійної освіти Боско»** повною мірою відповідає всім поставленим вимогам виробничої практики:
- Реалізовано чистий, масштабований монорепозиторій із розділенням на бекенд (`/cms`) та фронтенд (`/frontend`).
- Налаштовано взаємодію Payload CMS з хмарною базою даних Neon PostgreSQL, що забезпечує довговічність даних у серверлес-середовищі Vercel.
- Створено модульний клієнт на Vite, TypeScript та Vanilla JS із гнучким механізмом блокового рендерингу та якісним управлінням станами UI.
- Застосовано строгу типізацію TypeScript (Type Aliases, Discriminated Unions, Intersection Types та Type Guards).
- Проєкт повністю готовий до розгортання, демонстрації та захисту звіту з практики.
